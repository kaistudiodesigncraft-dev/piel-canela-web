# H4 — Editor administrativo de reserva configurable

Fecha de cierre: 2026-11-03 (America/Buenos_Aires)

## Resultado

H4 quedó implementado y validado exclusivamente en código y Supabase local.
Producción no recibió migraciones, despliegues, escrituras ni cambios de
contenido.

El panel incorpora una ruta separada por tratamiento:
`/admin/catalogo/[id]/configuracion-reserva`. Desde allí un administrador puede
preparar, simular y habilitar el circuito configurable de tratamientos nuevos,
sin alargar el editor general y sin convertir tratamientos históricos.

El circuito histórico no se detecta por nombre, slug ni ID. Cualquier
tratamiento con `config_enabled=false` y `selection_mode` distinto de `simple`
se muestra en modo de solo lectura. Por eso Depilación conserva sus tablas, RPC,
precios, zonas, combos y reservas sin alteración.

## Alcance funcional

- Modalidades configurables: simple, opciones, combos cerrados y combos con
  adicionales.
- Paquetes visibles como próximo release, pero bloqueados para activación.
- Etiquetas singular/plural, mínimo y máximo de selecciones, selección simple o
  múltiple, condiciones y descuento propio por tratamiento.
- Catálogo neutral de opciones y propuestas, sin reutilizar ni modificar las
  tablas históricas de Depilación.
- Estados borrador/activo; no existe borrado destructivo desde este editor.
- Simulador administrativo basado en el mismo `booking-engine` del servidor.
- Confirmación explícita antes de cambiar la modalidad de un tratamiento con
  reservas.
- Control de concurrencia mediante `updated_at` para evitar sobrescribir cambios
  realizados en otra sesión.
- Errores por campo y código de soporte sin registrar datos personales.

## Objetos SQL agregados

1. `public.save_treatment_option_combo_v1`: RPC `SECURITY DEFINER`, disponible
   únicamente para `authenticated`, que valida rol administrador y guarda una
   propuesta con sus relaciones dentro de una sola transacción.
2. `public.protect_active_treatment_option_usage`: trigger interno que impide
   pausar o invalidar una opción utilizada por una propuesta activa.
3. `public.enforce_configured_treatment_readiness`: trigger interno que impide
   habilitar una configuración incompleta o incompatible.

Las funciones internas de trigger no son ejecutables por `PUBLIC`, `anon` ni
`authenticated`; solo figuran para el propietario `postgres`. La migración H4 no
redefine funciones, policies, tablas o RPC históricas.

## Política de migraciones

Guardar un SQL en `supabase/migrations/` o hacer `git push` **no lo aplica por sí
solo en producción**. El flujo adoptado es:

1. cada cambio de base nace como migración versionada con rollback;
2. se valida con `db push --dry-run` y se aplica automáticamente por CLI en la
   base local;
3. se ejecutan pruebas, lint, rollback y verificador;
4. para producción se genera un respaldo fresco, se exige cero deriva
   bloqueante y se obtiene autorización explícita;
5. recién entonces la misma migración versionada se aplica por CLI o CI y queda
   registrada en el ledger de Supabase.

El editor SQL del Dashboard deja de ser un segundo origen de verdad. Solo se
usará de manera excepcional y cualquier intervención deberá convertirse en una
migración reconciliada en el repositorio.
